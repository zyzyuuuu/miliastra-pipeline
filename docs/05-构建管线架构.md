# 构建管线架构

## 四层

```
┌─────────────────────────────────────────────┐
│  规则层  core.js                             │  数值、概率、目标、物价
│          纯数据 + 纯函数，不碰任何 UI         │  网页版和沙箱版共用同一份
└────────────────┬────────────────────────────┘
                 │ require
┌────────────────▼────────────────────────────┐
│  呈现层  art.js（图元）  sprites.json（精灵） │  形状怎么画，不决定画什么
└────────────────┬────────────────────────────┘
                 │
┌────────────────▼────────────────────────────┐
│  构建层  build-native.mjs                    │  生成控件树 + Lua
│          克隆官方存档骨架，注入自己的内容      │  输出中间产物
└────────────────┬────────────────────────────┘
                 │ encodeGi
┌────────────────▼────────────────────────────┐
│  校验层  checkGi / checkUiTree / lint        │  产物合法性
│          场景测试 1,020 项断言                │  行为正确性
└─────────────────────────────────────────────┘
```

**分层的唯一目的**：改数值不用碰界面，改界面不用碰数值，改完能立刻验证。

## 为什么克隆而不是从零建

我试过从零建基础关卡，导入失败（踩坑清单第 7 条）。

所以改成：拿官方教学存档当基底，保留所有看不懂的结构，只做三件事——删掉它的示例控件、注入自己的控件树、注入自己的 Lua。

```js
const f = readGi('official-client-script-sample.gil');

// 1. 先验证读进来再写出去，字节完全一致。
//    这一步是整个流程的地基，跑不过就别往下走。
if (!encodeGi({ kind: f.kind, root: f.root, version: f.container.version })
      .equals(fs.readFileSync(src))) {
  throw Error('官方存档往返不一致');
}

// 2. 找到要接管的那棵 UI 子树
const tree = buildUiTree(f.root);
const ownerId = [...tree.scripts.values()][0];
const owner = f.root.ui.nodes.find(n => n.guid === ownerId);

// 3. 清空它的子节点
removeChildren(ownerId);

// 4. 从这里开始都是自己的东西
const canvas = clone('container', 'GameCanvas', owner);
```

**byte-preserving 往返验证**必须先跑通。它保证你后面所有的改动都只来自你的代码，不是来自编解码器的副作用。没有这一步，出问题你会分不清是"我写错了"还是"工具把文件弄坏了"。

这个验证救过我一次：某次工具版本升级后编解码有细微变化，往返验证立刻失败，问题被挡在源头。

## 原型克隆与 guid 重映射

官方存档里有几个"模板"控件：图片、文本、点击区域、容器。我不去构造这些节点的完整结构（槽位、类型标记、默认值一大堆），而是**克隆模板，只改它需要变的部分**。

```js
const prototypes = {
  image:     structuredClone(byName('圆圈图片')),
  text:      structuredClone(byName('分数文本')),
  area:      structuredClone(byName('圆圈点击区域')),
  container: structuredClone(byName('圆圈容器')),
};
```

克隆之后必须做 guid 重映射——节点内部有大量字段引用自己的 guid（父子关系、槽位绑定、事件监听），只改 `node.guid` 会造成半新半旧。

```js
function remap(o, from, to) {
  if (!o || typeof o !== 'object') return;
  for (const [k, v] of Object.entries(o)) {
    if ((k === 'v' || k === 'guid') && v === from) o[k] = to;
    else if (v && typeof v === 'object') remap(v, from, to);
  }
}
```

深递归重写，从根节点开始。新 guid 从 `0x40001000` 起顺序分配，避开官方存档已用的号段。

**这一步的坑**：如果漏掉某个引用路径（比如某个用了别的键名存 guid），会出现"控件存在但点不到"或者"文本显示在另一个位置"这种诡异现象。我遇到过一版是点击区域跟图片对不上，查了很久才发现是 area 原型里有一处 guid 引用没重映射。

## 中间产物不要手改

| 文件 | 性质 |
|---|---|
| `main.lua` | **手写**，运行时逻辑 |
| `build-native.mjs` | **手写**，构建脚本 |
| `main.generated.lua` | 生成物，由 build 注入数值后产出 |
| `controls.json` | 生成物 |
| `sprites-native.json` | 生成物 |

生成物一定会在下次构建时被覆盖。改它等于没改，而且会产生"我明明改了但没生效"的困惑。

数值一律改 `core.js`，然后重新构建。

## 校验分四类

| 类型 | 查什么 | 工具 |
|---|---|---|
| 结构 | 控件树是否合法、有无孤儿节点 | `checkUiTree` |
| 格式 | 存档整体是否可解析 | `checkGi` |
| 静态 | Lua 语法、明显错误 | `lint` |
| 行为 | 数值是否符合预期 | 场景测试（1,020 项断言） |

前两类是构建时自动跑的，后两类是手动的。

**场景测试要有项目**。纯结构检查只能告诉你"文件没坏"，不能告诉你"第 3 关的目标值算错了"。我的场景测试里有一组专门跑经济模型的：给定一套策略，模拟 20 关，检查钱包曲线是否落在设计区间。

## 一个反复出现的架构问题

`core.js` 同时被网页版和构建脚本引用，好处是数值同源，坏处是**它不能有任何副作用**。

我一开始在里面写了点 DOM 相关的辅助函数，原生构建时就炸了（Node 环境没有 `window`）。现在的规矩是：`core.js` 只允许纯数据结构和纯函数，所有环境相关的东西放到各自的入口文件里。

这条规矩的价值是：**改一次数值，网页版和沙箱版同时正确，不需要人工对齐。** 人工对齐这件事，做三次就会错一次。
