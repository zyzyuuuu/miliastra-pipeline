# 踩坑清单

十二条。每条都是真实撞上的，按"现象 / 原因 / 修法"写。前六条会直接毁掉你的一个版本。

---

## 1. 进关后一整块纯色，持续好几秒

**现象**：不是黑屏，是一块颜色固定的纯色（我的是 `#183438`），什么内容都没有，几秒后所有控件一次性出现。

**原因**：进关时把 `GameCanvas` 容器 `SetVisible(false)` 了，避免玩家看到控件逐个出现的半成品。容器一隐藏，它下面所有控件全部不可见，屏幕上只剩 `ScreenRoot` 下的全屏遮罩 `ScreenCover`——那块纯色就是遮罩本身。初始化跑完才 `SetVisible(true)`。

**修法**：两条一起做。一是砍初始化调用次数（`docs/02`）；二是在 `ScreenRoot` 上做一块加载幕撑住这段时间。

---

## 2. 做了加载幕，屏幕上还是空的

**现象**：加载幕的代码明明跑了，但进关还是纯色空屏。

**原因**：加载幕挂错父节点了。挂在 `GameCanvas` 下，容器一 `SetVisible(false)` 就跟着一起消失了。

**修法**：加载幕必须是 `ScreenRoot` 的直接子节点。代码里我分成两套辅助函数：

```js
function img()  { /* 挂 GameCanvas */ }
function rimg() { /* 挂 ScreenRoot，加载幕专用 */ }  // r = root
```

**判断方法**：任何"游戏开始前就要显示"的控件，都挂 root。

---

## 3. 提高分辨率之后，画质反而更糊了

**现象**：立绘从 64px 提到 192px，控件数涨了四倍，但人物看起来没有变清楚，甚至更糊。

**原因**：块外扩用了固定像素值 `+0.8`。显示尺寸固定不变，所以源分辨率越高、每块在屏幕上越小、0.8 占比越大。64px 时占 10%（刚好闭缝），192px 时占 31%（每块膨胀三成再重叠），把刚加回来的细节盖掉了。

**修法**：

```js
const ov = Math.min(1.2, Math.max(0.3, bw * scale * 0.12));
```

**通用规则**：同一份代码支持多种分辨率时，所有长度单位必须是相对的。

---

## 4. 某个图标显示成一个问号 "?"

**现象**：资源库图标位置出现一个"?"占位符，不报错，不崩溃。

**原因**：图标编号写错了。引擎找不到对应资源，用占位符代替。

**修法**：编号必须核对过再用。我的做法是在 `assets/SOURCES.md` 里记下每个编号的来源（截图文件、验证日期），事后能追。同类问题还有一个变体：本地离线渲染器只认硬编码的图标表，表里没有的会画成白块——这时候要分清是"真机没有这个资源"还是"渲染器没实现"。

---

## 5. 奇匠 Lv.1 的时候文字全部不显示

**现象**：低等级账号进关，所有文本控件空白，图片正常。

**原因**：未查明。升到 Lv.2 之后自行恢复。

**修法**：没有修法，只有规避——**别在低等级账号上做最终验收**。这条留在这里是因为它会让人误判成"代码写错了"，然后花半天去查文本控件的槽位结构。

---

## 6. 测试突然大面积失败，报的却是空字符串断言

**现象**：改完控件数量之后，跑测试一堆断言失败，失败原因都是"读到空字符串"。

**原因**：测试脚本模拟初始化时按固定的帧数跑（比如 115 帧），这个帧数是按上一版的控件数量标定的。控件从 7,933 涨到 18,415 之后，115 帧根本初始化不完，测试读到的是还没初始化的控件。

**修法**：**帧数必须跟着控件数走。**

```js
// 7,933 个控件，每帧 96 个 → 需要 87 帧，留余量取 115
t.fresh({}, 115);

// 18,415 个控件 → 需要 192 帧，取 260
t.fresh({}, 260);
```

**教训**：所有"按上一版数据标定"的常量，都是一个定时炸弹。改数据的同时必须搜一遍这类常量。

## 7. 自己做的关卡传不上去

**现象**：从零自建的基础关卡，导入试玩失败。

**原因**：不清楚，可能是缺少某些必需的结构节点。

**修法**：**拿官方教学存档当基底，克隆它的骨架，只往里加自己的东西。** 这是整个项目里最省时间的一个决定——绕过了所有"这个节点是干什么用的"的逆向工作。

具体做法见 `docs/05-构建管线架构.md`。代价是你得接受一堆看不懂的残留结构，但 byte-preserving 往返验证能保证你没破坏原档。

## 8. 布局烘焙进存档之后，界面全乱了

**现象**：为了砍掉每控件 5 次布局调用，把位置尺寸直接写进存档节点。结果控件全部堆在左上角。

**原因**：这是我在 v0.19 做的一个**假设**——假设引擎加载时会读取存档节点里的静态布局字段。这个假设没有官方文档背书，可能在某些情况下不成立。

**修法**：README 里必须写清楚回退方法。我的做法是保留两套路径：默认走烘焙，出错就恢复逐控件 `pos()` + `SetAsLastSibling`。

**教训**：**建立在假设上的优化，交付时必须写明假设和回退方式。** 否则下一个人（或者三个月后的你）会以为是别的地方坏了。

---

## 9. 导入报"空间不足"，但文件明明没超 20 MiB

**现象**：文件 17.8 MB，上限 20 MiB，导入失败。

**原因**：编辑器吃的是解包后的控件树体积，跟压缩后的文件大小不是一个数。实测占用到 92% 左右就开始报错。

**修法**：按 **88~89% 就停手**来设计，留出余量。用 `node src/budget.mjs` 提前算，别等导入才知道。

---

## 10. 测试跑到一半进程崩了

**现象**：整套场景测试连续跑，跑到某一部分进程直接退出，没有报错信息，或者报堆内存超限。

**原因**：单进程堆内存到了 V8 默认上限（约 4 GB）。测试要加载完整的控件树，18,000 个控件加上 Lua 模拟状态，很吃内存。

**修法**：**拆成多个进程分别跑**，一个进程跑一部分。我是拆成 4 个，合计 1,020 项断言。

**别做的事**：把堆上限调到 8 GB。机器只有 16 GB，调上去会让整机交换，更慢。

## 11. 想用 RLE / 调色板量化压缩块数，几乎没用

**现象**：把 96×96 的立绘从真彩降到 24 色，块数只从 2,545 降到 2,257，降了 11%。

**原因**：那张图有 2,454 种颜色——它不是像素画，是官方立绘下采样来的近似连续图像。块数的决定因素不是"颜色总数"，而是"相邻区域颜色变化的密度"。量化只是让每种颜色变少，没有减少变化的位置。

**修法**：别在颜色上做文章。真正控制块数的是**分辨率**和**容差**两个旋钮，标定表见 `docs/01`。

---

## 12. 同一次点击穿透到了下一个界面

**现象**：过关画面点一下进商店，结果同一次点击直接把抽卡也触发了。

**原因**：按键/点击事件在界面切换时被连续处理，没有等待释放。

**修法**：界面切换后加两道保护——**等按键释放**，以及**经过一段保护时间**再启用点击。失败结算画面同理，倒计时结束前不能重开。

**这类问题在真机上才明显**，本地模拟环境里点击是瞬时的，很难复现。凡是"切换界面 + 立刻可点击"的地方，都预先加一道保护。

---

## 附：两条非技术的坑

**存档没有云存储。** 玩家退出关卡，命座、粉球、保底进度全部重置。要做跨局进度，得自己在关卡里用变量存，或者接受"每次进来都是新的"。

**网页版和原生版的数值必须同源。** 我把所有数值放在一个 `core.js` 里，原生构建时从这个文件序列化。改规则必须改这一处，不要两边各改一份——我第一次就是两边都改了，改完不一致，花了半天对齐。
