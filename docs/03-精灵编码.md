# 精灵编码：把一张 PNG 拆成 4,686 个矩形

## 约束

千星沙箱的 UI 控件里，**没有"显示一张图片"这个接口**。你能用的只有矩形、圆、文本。

想在关卡里显示一个角色立绘，只能把图拆成一堆彩色矩形，用几千个 image 控件拼回去。听起来荒谬，但它确实是可行路径——只要拆得够聪明。

## 为什么不用固定网格

最直觉的做法是切成 16×16 或 32×32 的网格，每格取平均色。这个方案有两个致命问题：

1. **纯色区域被过度细分。** 一片纯色背景切成 256 块，其实 1 块就够。
2. **复杂区域不够细。** 眼睛、发丝、边缘这些地方 16px 格太大，糊成一团。

所以我用的是**递归四分**：一块区域先算颜色方差，够纯就整块保留，不纯就对半切开再试，直到 1×1。

```js
function walk(x, y, w, h) {
  // 1. 统计这块的平均色和标准差
  // 2. 整块接近全透明 → 直接丢弃，不生成任何控件
  if (hi < alphaMin) return;

  // 3. 够纯 → 保留成一块
  const clean = error <= tolerance && (hi - lo) <= alphaRange;
  if (clean || (w === 1 && h === 1)) {
    blocks.push([x, y, w, h, ...avg]);
    return;
  }

  // 4. 不纯 → 沿长边对半切，分别递归
  if (w >= h && w > 1) {
    walk(x, y, Math.floor(w / 2), h);
    walk(x + Math.floor(w / 2), y, w - Math.floor(w / 2), h);
  } else {
    walk(x, y, w, Math.floor(h / 2));
    walk(x, y + Math.floor(h / 2), w, h - Math.floor(h / 2));
  }
}
```

三个设计点：

**判据用标准差，不用颜色差异。** 拿块内每个通道的标准差，取最大值。这比"最大色差"稳定，因为它反映的是整块的离散程度，不会因为一个噪点就误判。

**透明区域直接丢弃。** 立绘的背景通常占 30~50%，这些区域如果生成控件就是纯浪费。判据是"块内 alpha 最大值低于阈值"，注意是 `hi`（最大）不是 `avg`（平均）——边缘的半透明块要保留。

**沿长边切。** 保证切出来的块尽量接近正方形，视觉效果更自然，也避免出现细长条（细长条在缩放时的取整误差更大）。

## 外扩闭缝：最容易踩的一个坑

块是矩形，坐标要取整。取整之后，相邻块之间会留下不到 1px 的缝，整体看上去是网格或者斜纹。

标准解法是让每块稍微放大一点，压住缝。**问题在于"一点"是多少。**

v0.19 我写的是固定 `+0.8px`。在 64px 立绘上效果很好，缝完全消失，细节也在。到 v0.20 把立绘提到 192px，同一个 0.8 出事了——细节被糊掉了。

原因反直觉，值得单独讲：

**这里的"显示尺寸是固定的"。** 人物在界面上的占位是 245~270 个布局单位，跟源图分辨率无关。所以：

- 64px 源图，缩放比 ≈ 3.83，一块 2 像素宽的块在屏幕上约 **7.7 单位**
- 192px 源图，缩放比 ≈ 1.28，同样 2 像素宽的块在屏幕上只剩 **2.6 单位**

同一个 `+0.8` 的外扩量：

| 源分辨率 | 块在屏幕上的宽度 | 0.8 占的比例 | 效果 |
|---|---|---|---|
| 64px | ~7.7 单位 | **10%** | 刚好闭缝，不失真 |
| 192px | ~2.6 单位 | **31%** | 每块膨胀三成再重叠，细节全糊 |

**分辨率越高，固定外扩量的占比反而越大。** 因为图变细了、块变小了，但外扩量是个常数。

所以"提分辨率能提升画质"这件事，会被一个没跟着改的常数直接抵消掉。你以为在加细节，其实在把细节盖住。

正确写法是让外扩量跟着块的尺寸走：

```js
const ov = Math.min(1.2, Math.max(0.3, bw * scale * 0.12));
```

- `bw * scale` 是这块在屏幕上的实际宽度
- `× 0.12` 取 12% 作为外扩量
- `min(1.2, ...)` 防止大块外扩过多
- `max(0.3, ...)` 防止小块因取整而消失

这个公式在 64px 和 192px 上都能正确工作，因为它跟块的大小挂钩，不跟常数挂钩。

> 教训：**任何跟像素尺寸相关的常量，先问一句"换个分辨率还成立吗"。** 不成立的，就该改成比例。
>
> 更普遍地说：**同一份代码要支持多种分辨率，所有长度单位都必须是相对的。** 混进一个绝对像素值，它只会在某一个分辨率上正确，而且失效的时候不报错，只是变糊。

## 为什么 RLE 和调色板量化救不了

我一度想：既然块数太多，那能不能用 RLE（游程编码）压缩相邻同色块？或者先做调色板量化，把颜色数降到 24 色，块数自然就少了？

实测否掉了这个方向。原因是源图的特性：

**96×96 的立绘里有 2,454 种颜色。**

这不是像素画，是从官方立绘下采样得到的近似连续的图。头发的高光、脸颊的红晕、衣服的渐变，每一处都是大量细微色差。这种图做调色板量化，会立刻出现色块断层（banding），而且——

**块数降不下来。** 实测从原色彩降到 24 色，块数从 2,545 只降到 2,257，降了 11%。因为块数的决定因素不是"颜色总数"，而是"相邻区域的颜色变化密度"，量化只是把每种颜色变少，没有减少变化的位置。

所以正确做法不是压缩，是**在源头降分辨率 + 调容差**。这两个参数才是真正控制块数的旋钮。

## 一条前置建议

**动手编码之前，先翻一遍编辑器自带的图片资源库。**

物品、货币、宝箱、箭头、边框这些东西，资源库里基本都有原生图标。原生图标是分辨率无关的，一个控件搞定，放大到任意尺寸都清晰。

我把摩拉从"123 块 × 24 份"换成原生图标 `111136`，控件数从约 2,950 降到 24，画质还变好了。

自己编码只应该用在**资源库里没有的东西**上，主要就是角色立绘。

（编号必须核对过。写错编号不会报错，会直接显示成一个"?"占位符。）
