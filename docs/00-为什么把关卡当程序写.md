# 为什么把关卡当程序写

先说结论：**代码化不是为了少点几下鼠标，是为了让你敢改。**

## 手工工作流的真实成本

千星编辑器的操作方式是把控件拖到画布上、在属性面板里填数、在节点图里连线。做十个控件，这套流程没问题。做一万个，它会变成这样：

- 想把第 1—20 关的目标值整体下调 8%。手工做法是打开 20 个关卡设置逐个改，改完还要重新通关验证。
- 想调整六档命座的条件概率（10% / 25% / 40% / 60% / 100%），得先在纸上算期望抽数，再回编辑器改六个参数，再模拟一遍看是不是还落在"平均 3.1 抽出货"。
- 想知道"普通玩家大概能过第几关"，只能自己玩、或者找人来玩。

这三件事的共同点是：**验证一次的成本太高，所以你只会验证一次。**

我当时面对的具体决策是：首关要让大多数人过，普通玩家到第 10 关左右，熟练玩家 13—15 关。这个设计目标如果不跑模拟，就只能靠感觉。而凭感觉调的数值，玩家会立刻发现——"第 12 关就是卡人的"。

所以我把规则全部抽到一个 `core.js` 里，用脚本跑了整条曲线：每关目标、物品期望收益、炸弹收益期望、商店投入产出、命座概率对通关率的实际影响。脚本跑一轮是秒级，改一次参数重跑也是秒级。

**只有能快速验证的方案，才会被真的验证。**

## 代码化的边界在哪

这套东西不是万能的，划清边界比吹它有用更重要：

| 适合用代码 | 不适合 |
|---|---|
| 界面骨架（几十上百个控件的坐标、颜色、字号） | 美术构图好不好看 |
| 数值（目标、概率、价格、期望） | 手感（钩子摆动速度、回收手感） |
| 重复性控件（立绘、物品槽、遮罩） | 特效节奏、动画曲线 |
| 本地校验（控件树合法性、Lua 静态检查） | "这个关卡好不好玩" |

一条实用判据：**如果一个决策需要被反复计算，就用代码；如果它需要被"感觉"，就用鼠标。**

美术和手感必须手工调，这是编辑器存在的意义。但数值和重复控件必须代码化，因为你会改二十遍。

## 付出的代价

诚实地说三条：

1. **你得会写 JS。** 这不是给非程序员的工具。
2. **调试链路变长。** 本地渲染器只能近似，最终效果必须导入真机看。我踩过最亏的一次是本地看着没问题、真机上文字不显示（见踩坑清单第 5 条）。
3. **构建脚本本身会变成新项目。** 我的 `build-native.mjs` 最后有 21KB，测试脚本比业务代码还长。

如果只是做一个三分钟能玩完的小关卡，别用这套。它的回本点在"你打算改很多次"。

## 所以这个仓库给什么

不给成品，给三样东西：

- **两个能直接跑的脚本**：预算计算器、精灵编码器
- **六个模型**：预算、性能、编码、踩坑、管线、成本
- **一组真实的数字**：18,415 控件、142,908 次调用、1,020 字节/控件、192 帧

数字比结论值钱。结论会过时，标定方法不会。
