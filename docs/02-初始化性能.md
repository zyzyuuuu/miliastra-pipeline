# 初始化性能：142,908 次 UI 桥调用

## 现象

用户的原话是"一进去就蓝屏五秒"。

不是崩溃，不是闪退。屏幕上是一整块 `#183438` 的纯色，什么都没有，整整五秒，然后所有东西一次性出现。

这个描述给了我两个关键信息：**它是稳定复现的五秒**，不是随机卡顿；**它是纯色不是黑屏**，说明游戏画面被隐藏了，而不是没渲染出来。

## 完整链路

顺着这两条查下去，链路是这样的：

1. 进关时 `main:SetVisible(false)` 把整个 `GameCanvas` 容器隐藏了——这是为了避免玩家看到控件逐个出现的半成品画面。
2. `GameCanvas` 一隐藏，它底下的一万多个控件全部不可见，屏幕上只剩下 `ScreenRoot` 下的 `ScreenCover`——一块 1920×1080 的 `#183438` 纯色遮罩。
3. 初始化函数 `initialize()` 要逐个处理控件，每帧只处理固定数量。
4. 处理完最后一帧，`SetVisible(true)`，全部控件一次性显示。

**所以那五秒"蓝屏"，本质是初始化的耗时被完整暴露在了玩家眼前。** 隐藏容器这个设计本来是好的（避免半成品画面），但它把耗时从"看不见的加载"变成了"看得见的空屏"。

## 数学推导

这一步值得单独讲，因为它是整个排查里唯一能落地的证据。

v0.18 的控件数是 **11,037**。每个控件在初始化时大约要跑 **13 次 UI 桥调用**（可见性、层级、五个布局属性、坐标等）。

```
11,037 控件 × 13 次 = 142,908 次桥调用
```

每帧处理 128 个控件：

```
11,037 ÷ 128 = 87 帧
```

用户观测到的耗时是 5.0 秒左右，87 帧在 60fps 下是 1.45 秒。差了三倍多——说明每帧处理 128 个控件这个节奏本身也在被拖慢。

反推单次调用成本：

```
5.0 秒 ÷ 142,908 次 ≈ 35 微秒/次
```

35 微秒对一次跨语言桥调用（Lua → 引擎）是完全合理的量级。**推导和观测对上了，这就是根因。**

> 诚实标注：35µs/次是反推值，不是单点实测。但 5.0 秒这个锚点是用户实测的，推导链条闭合，可信度足够支撑优化决策。离线环境测不出真实桥调用延迟，这一点必须承认。

## 三类能砍的调用

拆开这 13 次，能砍的只有三类：

### 一、`SetAsLastSibling`（每控件 1 次）

原本对每个控件都调一次，目的是把兄弟顺序排对。

**但兄弟顺序本来就由构建顺序决定**——控件是按创建顺序加进父节点的，天然就是正确顺序。这一万多次调用是纯浪费。

砍掉：**−11,037 次**，占总量 7.7%。

### 二、五个布局属性调用（每控件 5 次）

每次都要设位置、尺寸、锚点等五个属性。

关键做法：**在构建阶段就把这些值烘焙进存档节点的静态字段里**。存档本身是结构化数据，加载时引擎会直接读这些字段，不需要 Lua 运行时再设一遍。

砍掉：**−55,185 次**，这是最大的一块。

⚠️ 这一步的前提是"烘焙进存档的值会被引擎正确读取"。这是个假设，不是官方文档保证的行为。我在 README 里写了回退方法：如果布局错乱，恢复逐控件 `pos()` 调用即可。

### 三、可见性调用（每控件 1 次）

初始化完才显示，所以每个控件都要 `SetVisible(true)`。

这一条**不能全砍**——静态装饰件（背景、边框、分隔线）确实需要显示。但**可以按组批量控制**：把同组的控件挂到一个容器下，只设容器的可见性，而不是逐个设。

## 结果与拆分

| | v0.18 | v0.19 | 变化 |
|---|---|---|---|
| 控件数 | 11,037 | 7,933 | −28% |
| 每次控件调用数 | 13 | 4 | −69% |
| 桥调用总数 | 142,908 | 32,400 | **−77%** |
| 每帧处理数 | 128 | 128 | — |
| 初始化帧数 | 87 | 62 | — |

**必须拆开说**：−77% 里有一部分来自控件数减少（7,933 vs 11,037），不全是优化功劳。纯优化贡献是每控件 13→4 次这一项。

如果只砍调用、控件数不变，11,037 × 4 = 44,148 次，降幅是 69%，不是 77%。引用数字时别把这两件事混起来。

## 关键公式

初始化时长基本是线性的：

```
时长 ≈ 控件数 ÷ 每帧处理数 ÷ 60（fps）
```

- v0.19：7,933 ÷ 128 ÷ 60 ≈ 1.03 秒（实测 1.1~1.5 秒）
- v0.20：18,415 ÷ 96 ÷ 60 ≈ 3.20 秒（实测约 3.2 秒）

v0.20 的每帧处理数从 128 降到 96，是我在画质优先（控件数翻倍）的前提下主动调低的，为了给单帧留余量。**每帧处理数是个可调旋钮，它直接决定加载时长。**

## 但真正该做的是加载幕

优化到 4 次调用/控件之后，我发现一件事：**18,415 个控件也只要 3.2 秒。**

也就是说，性能优化做到这个程度，加载时间已经不是主要矛盾了。真正的问题是——**那 3.2 秒里玩家看到了什么。**

v0.18 看到的是纯色空屏，所以感觉像"卡死"。v0.20 做了一块加载幕：

- 三层同心椭圆光晕拉出纵深
- 顶部金色圆环徽章
- 标题 + 三段装饰线
- 进度条，进度随初始化推进
- 底部一句"首次载入需数秒，之后会更快"

关键实现细节：**加载幕必须挂在 `ScreenRoot` 下，不能挂在 `GameCanvas` 下。** 因为 `GameCanvas` 被 `SetVisible(false)` 隐藏时，它所有的子控件——包括加载幕——都会一起消失。我第一次就是挂错了地方，屏幕上还是空的。

```js
// 正确：挂到 ScreenRoot
rimg('LoadDim', 500, 300, 1920, 1080, '#08161a');
rtext('LoadTitle', 500, 212, 900, 66, '正在点亮矿洞…', 44, '#f4e4bd');

// 错误：挂在 GameCanvas 下，会被一起隐藏
```

而且加载幕**只能用基础形状**（100001 矩形 / 100002 圆）搭，不要引用没核对过的图标编号——编号错会显示成"?"，在加载幕上出现一个问号比空屏更难看。

## 三条可复用的判断

1. **启动慢先数调用次数，别猜引擎。** 控件的"单价"是次数，不是数量。
2. **隐藏容器会把耗时变成可见的空屏。** 要么别隐藏，要么用加载幕撑住它。
3. **优化到头之后，问题会从"多久"变成"期间看到什么"。** 这两个是不同的问题，别用第一种思路解第二种。
