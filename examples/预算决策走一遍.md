# 示例：从一张立绘到预算决策

不是可运行的 demo（那需要你自己的美术资源和官方存档），是一份**决策记录**——照着走一遍，你会得到自己的数字。

假设要做一个人物立绘，显示尺寸 245×245 布局单位。

---

## 第一步：先算预算，不看画质

```
总预算 18,500 控件（20 MiB 留 10% 余量）
```

先问自己还剩多少。如果这是第一个人物，你有充足空间；如果是第五个，先跑一遍：

```bash
node src/budget.mjs --controls 12000 --margin 10
```

看"余量"那一行。剩余控件数 ÷ 1000 大致就是还能加几个 192px 人物（一个人物约 4,700~6,600 块）。

## 第二步：算这个尺寸需要多少像素

显示 245 单位，1.6 倍缩放 ≈ **392 屏幕像素**。

源图如果只有 96px，要放大 4 倍才会填满——糊是必然的。所以源图边长至少要接近屏幕像素数。

---

## 第三步：跑三档，挑一档

```bash
node src/compile-sprites.mjs --in ./assets --out ./out.json \
  --spec hero_160:hero.png:160:34 \
  --spec hero_192:hero.png:192:38 \
  --spec hero_192c:hero.png:192:42
```

三档的块数大致会落在这类比例上（实测对照见 `docs/01`）：

| 档位 | 块数 | 体积 | 适用 |
|---|---|---|---|
| 160 / tol 34 | ~5,000 | ~4.9 MiB | 预算紧张时 |
| 192 / tol 38 | ~4,700 | ~4.6 MiB | 推荐 |
| 192 / tol 42 | ~4,200 | ~4.1 MiB | 差一口气时 |

**先调容差，最后才降分辨率。** 容差从 38 提到 42 能省 13%，画质几乎看不出；分辨率降一档是肉眼可见的损失。

## 第四步：外扩量别写死

```js
// 别这样
const ov = 0.8;

// 这样
const ov = Math.min(1.2, Math.max(0.3, bw * scale * 0.12));
```

固定值只在某一个分辨率上正确。换分辨率必须换成比例。

## 第五步：确认体积

```bash
node src/budget.mjs --controls 18415 --sprites hero:4686 --margin 10
```

占用超过 90% 就回去调容差。**别靠导入报错来发现问题**——那时候你已经做完了。

---

## 一个反例

我第一版是这么做的：

1. 先担心加载太慢
2. 把 96px 降到 64px，省了 10,000 个控件
3. 加载从 5 秒降到 1.5 秒，很满意
4. 导入真机，人物是马赛克
5. 回滚到 192px，加载变成 3.2 秒
6. 发现 3.2 秒根本不是问题，5 秒那次是初始化写错了

**顺序错了，所以白干了一天。**

正确的顺序是：先确定画质要什么 → 算出要多少控件 → 检查预算够不够 → 最后才看加载时间够不够。
