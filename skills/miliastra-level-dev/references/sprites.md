# 精灵编码：PNG → UI 矩形

千星 UI 控件没有"贴图"接口，只有矩形/圆/文本。显示立绘 = 拆成彩色矩形拼回去。

## 算法：递归四分（不是固定网格）

- 块内颜色标准差 ≤ 容差 → 整块保留
- 块内 alpha 最大值 < 阈值 → 丢弃（透明区不产生控件，立绘背景占 30~50%）
- 否则沿长边对半切，递归到 1×1

为什么不是网格：纯色区被过度细分、复杂区不够细，同等画质块数多得多。

## 三个关键参数

| 参数 | 推荐值 | 说明 |
|---|---|---|
| 边长 | 192 | 显示 245 单位（≈392 屏幕像素）时的交点；224 是陡坡 |
| 容差 | 38 | 42 省 13% 块数，画质几乎不变 |
| alpha 阈值 | 12（丢弃）/ 极差 70 | 用 `hi`（最大值）判丢弃，不是平均值，边缘半透明块要保留 |

## 外扩闭缝（最容易错的一处）

块坐标取整会留 <1px 缝 → 每块稍微外扩盖住。**外扩量必须按比例：**

```js
const ov = Math.min(1.2, Math.max(0.3, bw * scale * 0.12));
```

反直觉的机制：**显示尺寸固定**（如 245 布局单位），源分辨率越高、每块在屏幕上越小，同一个固定像素外扩的占比反而越大——64px 源时占块宽 10%（正确），192px 源时占 31%（细节被盖掉）。这就是"提高分辨率反而更糊"的原因。

通用规则：同一份代码支持多分辨率时，所有长度单位必须是相对量。

## 为什么 RLE / 调色板量化没用

官方立绘下采样图不是像素画（96×96 含 2,400+ 色）。块数由"相邻区域颜色变化密度"决定，不由颜色总数决定：降到 24 色只减块 11%，且出现色带。控制块数只用两个旋钮：分辨率、容差。

## 工具

```bash
# sharp 缺失时：npm i sharp 或 SHARP_PATH=/path/to/sharp
node scripts/compile-sprites.mjs --in ./assets --out ./sprites.json \
  --spec hero:hero.png:192:38 --spec coin:coin.png:48:28
```

输出含每张图块数与体积估算。先跑这个，再跑 budget.mjs 验证总预算。
